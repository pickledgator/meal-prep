# Meal Prep

Weekly dinner plans — menu, grocery list, Sunday prep, and recipe cards — generated by a Claude Code skill and served from a small self-hosted app.

**Live:** https://meal-prep-nic.fly.dev (shared password; set as the `APP_PASSWORD` Fly secret, never committed)

The hosting follows the marriotty pattern: the **writer runs locally** (plan generation in Claude Code, writing straight to Turso), and the **cloud app is read-mostly** (one Fly machine serving a Hono API + prebuilt SPA).

## Generating a new plan

From this repo, in Claude Code:

```
/meal-prep 5 meals, meals for 2 + leftovers
```

(flags work too: `/meal-prep --meals 5 --servings 2 --leftovers --theme italian`)

The skill asks its guided questions, proposes the menu in chat for approval, then:

1. checks past themes/recipes/marquee sauces against the live database — `pnpm history --json`
2. composes the whole week as one JSON payload at `payloads/<slug>.json`
3. validates it — `pnpm ingest payloads/<slug>.json --dry-run`
4. ingests it — `pnpm ingest payloads/<slug>.json` (writes to Turso using the credentials in `.env`)

The plan is live at `/plans/<slug>` immediately. **No deploy is involved** — plans are data; deploys only happen when app code changes.

### Fixing / replacing / removing a week

- **Replace**: re-ingesting the same slug fully replaces that plan (edit the payload or re-run the skill, then `pnpm ingest` again).
- **Delete**: `curl -X DELETE -u ":$APP_PASSWORD" https://meal-prep-nic.fly.dev/api/plans/<slug>`
- **Inspect**: `pnpm history` lists everything in the database.

The payload contract lives in `shared/src/meal-plan.ts` (zod), documented for the generator in `.claude/skills/meal-prep/reference/output-format.md`.

## Local development

```bash
pnpm install
pnpm dev        # API on :8788 + Vite on :5174 (concurrently)
```

Open **http://localhost:5174**. With no `.env`, the server uses `server/local.db` and auth is disabled. Ports default to 8788/5174 so they don't collide with the trip-planning dev servers on 8080/5173; override with `PORT=<n> pnpm dev` (the Vite proxy follows).

Rebuild the local database from scratch:

```bash
pnpm db:push    # create/update schema (server/local.db)
pnpm backfill   # re-import all plans from the frozen plans/ archive
pnpm backfill --verify
```

With Turso credentials in `.env`, the same commands (and `pnpm ingest`) target production instead of the local file — that's the point.

## Deploy & ops

Pushing to `main` deploys automatically (`.github/workflows/deploy.yml`, `FLY_API_TOKEN` repo secret). Manually:

```bash
./deploy.sh            # build + deploy
./deploy.sh secrets    # push TURSO_DATABASE_URL / TURSO_AUTH_TOKEN / APP_PASSWORD from .env
./deploy.sh db         # drizzle-kit push against the DB in .env
./deploy.sh status|logs|open
```

Copy `.env.example` → `.env` for credentials. Auth is a single shared password over HTTP Basic; `GET /api/health` is the only unauthenticated route (Fly checks).

## Layout

```
shared/    zod PlanPayload contract — single source of truth for API shapes
server/    Hono API + Drizzle/Turso + CLIs (ingest, history, backfill)
web/       Vite + React SPA (wouter, tanstack-query)
plans/     FROZEN pre-database markdown archive — nothing reads or writes it
.claude/skills/meal-prep/   the generator skill
```

One always-on `shared-cpu-1x` Fly machine (sjc) + a Turso database (aws-us-west-2). Prep-list check-offs are stored per device in localStorage.
